## 0. 结论（TL;DR）

1. **丢交互，不丢模型。** 终端的键位表（PgUp/PgDn、↑↓ 历史、Tab、Esc 语义）和"整屏 = 一个界面"
   的假设要丢掉；但 rig-tui 编码的**领域模型**（turn / call / Ask / Picker / StatusItems /
   RenderBatch+look）不是"终端设计"，它是 agent 运行时的状态机——换成空间 UI 一模一样，不能丢。
2. **Bevy ECS + 3D 的理由不是"3D 好看"，而是"UI 和 agent 在同一个 World 里"。** rig-ecs 本身是
   Bevy 插件；RealityKit 用 ECS + 声明式 UI 表达的架构，Bevy 有同构的对应物（§3）。
3. **visionOS 路线可行，但要说得准确：** 我们做的是**visionOS 级设计规范的 Bevy 实现**，
   不是"visionOS 应用"（Bevy 现在没有 visionOS 目标，Swift/Metal 桥超出范围）。
   借的是它的**交互规则（HIG）和架构范式（ECS + RealityView + 空间锚点）**，不是它的 API。

## 1. 3D 相对终端：哪些优势是真的

| 优势 | 是不是真的 | 说明 |
|---|---|---|
| 按**注意力**分配空间，而不是按行数挤 | ✅ 真的 | 终端里转写/输入/状态抢同一个 96×28 矩形；空间里卡片各有位置与大小，深度 = 层级 |
| **直接操作**（点、拖、缩放）替代背键位 | ✅ 真的 | 终端键位是专家界面；空间 UI"看得见就能动"，工作记忆负担低 |
| 多卡片**并排比较**（多个 agent、多个工具结果） | ✅ 真的 | 终端只能滚动；空间里可以并置（这正是 rig 多 agent 的天然形态） |
| **空间记忆**：卡片留在世界里的固定位置 | ✅ 真的 | HIG 的 spatial layout 原则；终端历史只存在滚动缓冲里 |
| **多模态**：凝视 + 捏合 + 语音 + 陀螺仪 | ✅ 真的 | 头显/手机没有物理键盘，键位表在这里根本不存在 |
| 材质/光照/动效传达状态 | ✅ 但易滥用 | 玻璃、发光能表达"浮层/焦点"，但滥用会变成"科幻电影道具" |
| 沉浸/专注（dimming、只留相关卡片） | ✅ 真的 | 对应 visionOS 的 immersion 分级 |
| **长文本/代码 diff/日志**更好读 | ❌ 反了 | 这类内容 2D 面板最优，终端/编辑器更快；空间 UI 要做的是**把它包进卡片**，而不是把它 3D 化 |
| **精确打字**更快 | ❌ 反了 | 头显里打字不如物理键盘；语音适合短指令，不适合长 prompt |
| 阅读舒适度全面更好 | ❌ 不一定 | 距离、字号、位图字体放大发糊都是真问题（§7） |

**结论**：3D 的赢面是"**布局与操作**"，不是"文字渲染"。所以别把力气花在"把终端字符网格变立体"，
要花在"卡片怎么摆、怎么动手"。这也是为什么我们已有的 `frame.rs`（行列布局、折行、截断、keep 优先级）
不是废料——它是**卡片内部的排版引擎**，而卡片本身才是新的东西。

## 2. 该丢什么、留什么

| 层 | 终端的做法 | 空间 UI 的做法 | 处置 |
|---|---|---|---|
| **键位/操作** | PgUp/PgDn 滚动、↑↓ 历史、Tab 打勾、Esc 关闭 | 凝视+捏合、拖拽、点击、语音 | **丢**（降级为辅助输入，见下） |
| **屏幕假设** | 一个 96×28 的整屏，所有面板都是它切出来的 | 空间里 N 张卡片，各有位置/朝向/大小 | **丢**，`Placement` 降级为"flat 模式" |
| **状态行** | 屏幕底部一行文本 | 卡片 footer / ornament | 改造（数据仍是 `StatusItems`） |
| **输入框** | 3 行编辑器 + 键位提示 | composer 卡片（文本 + 附件 + 语音 + 发送） | 改造（`Editor` 状态复用） |
| **转写** | 一整块滚动缓冲 | 转写卡片（可折叠成摘要卡、可展开成阅读卡） | 改造（`transcript`/`pane` 的内容逻辑复用） |
| **picker** | 盖住整屏的列表 + preview | 浮在空中的选择卡（列表卡 + 预览卡），或 radial/菜单 | 改造（数据模型 `Picker`/`Chosen`/`Ticked` 复用） |
| **补全** | 输入框上方的弹窗 | composer 卡片上方的候选 chips | 改造 |
| **领域模型** | turn/call/Ask/Picker/Notice/status | **一模一样** | **留** |
| **look 管线** | `RenderBatch` + `RenderSystems::Render` → `LookLine` | 卡片内容的生成器 | **留** |
| **内容排版** | 行列、折行、截断、keep/min_width | 卡片内部排版 | **留**（`frame.rs` 降级为卡片内部布局） |
| **键位提示** | "Enter sends · / commands · @ files" | "捏合选择 · 拖动移动 · 语音输入" | 改造（文案按输入模态变） |

**为什么"留"这么重要**：丢掉 `Ask/Picker/StatusItems/RenderBatch` 等于丢掉唯一的、被真实终端验证过的
行为规格。空间 UI 最难的不是"画得科幻"，而是"状态机不出错"——这部分 rig 已经写好了，我们只换外观和输入。

**键盘怎么办**：不删，**降级为辅助输入**。理由：
1. visionOS 本身就支持物理键盘/切换控制，无障碍要求有替代输入；
2. 我们现在的开发机没有头显，键盘是唯一能自动测的输入（巡游截图全靠它）；
3. 桌面 3D 窗口模式下，键盘+鼠标是主输入。
实现上：所有键位处理保留成 `KeyboardFallback`，主输入路径换成"指针/凝视 → 卡片 → 动作"。

## 3. 为什么是 Bevy ECS + 3D

### 3.1 真正的理由：UI 和 agent 在同一个 World

- rig-ecs 是 Bevy 0.20 插件；agent / turn / call / gate 都是实体。**"工具调用变成一张卡片"就是 spawn 一个实体**，
  不需要 IPC、不需要跨语言、不需要把状态序列化过去再序列化回来。
- 同一个 `Update` 里：工具 effect 结算 → look 生成行 → 卡片内容更新 → 布局 → 镜像成 3D。
  数据只有一份，变更检测（`Changed<T>`）就是"UI 什么时候要重画"的答案。
- 这正是 rig-tui 的架构（immediate-mode 终端渲染同一个 World），我们只是把"渲染器"换成"保留模式 ECS UI + 3D"。

### 3.2 RealityKit 的范式与 Bevy 的对应

Apple 在 [Understanding the modular architecture of RealityKit](https://developer.apple.com/documentation/visionos/understanding-the-realitykit-modular-architecture)
里明确说 RealityKit 基于 **Entity Component System**；[WWDC23 10080《使用 RealityKit 构建空间体验》](https://developer.apple.com/cn/videos/play/wwdc2023/10080/?time=576)
从 9:36 讲 entities/components、23:00 讲 custom systems。它的空间 UI 架构是：

```text
SwiftUI（声明式 2D 视图/窗口）
  └─ RealityView（把 3D 内容挂进视图）
       └─ RealityKit（ECS：Entity / Component / System、空间锚点、动画、音频）
```

Bevy 侧的同构物（我们已经在用）：

| RealityKit / visionOS | 我们的对应物 | 现状 |
|---|---|---|
| `Entity` | `Entity` | ✅ 同构 |
| `Component`（含 `ModelComponent`、`Transform`） | `Component` + `Transform`/`Node` | ✅ |
| `System`（`SceneUpdateContext`, custom systems） | Bevy `System` + `Update`/`PostUpdate` 调度 | ✅ |
| `RealityView` + attachments | `MirrorRoot` + `WorldPanel`（bevy_ui 子树镜像成 3D） | ✅ 已实现（route B） |
| 空间锚点（`AnchorEntity`、`SpatialTrackingSession`） | 我们的 `FrameGeometry`/卡片 `Pose`（世界坐标） | ⚠️ 只有"一帧平面"，没有 per-card 锚点 |
| 声明式状态（`@State`/`@Observable`） | `Resource` + `Component` + 变更检测 | ✅ |
| `Model3D` / `ModelEntity` | `Mesh3d` + `UNodeMaterial3d`（bevy_luma SDF） | ✅ 部分 |
| glass 材质、vibrancy | `UNodeMaterial3d` 半透明 + 背板 | ⚠️ 要调 |
| 手势/凝视（eyes & hands） | `bevy_picking` + 自定义 gaze/pinch | ❌ 还没有 |
| 空间音频 | `bevy_audio`（`SpatialListener`/`AudioSink`) | ❌ 未接 |

**所以"迁移经验"具体是迁移三样东西**：
1. **ECS 分层**：内容（model）→ 组件（pose/size/state）→ 系统（布局、交互、动画）分离；
2. **声明式 UI 数据流**：状态变 → 组件变 → 系统重排，而不是"命令式地往画布上画"；
3. **空间规则**（HIG）：布局、视线、舒适度、材质、层级——这是"工业标准"，照它做就不会飘。

### 3.3 为什么不是 Unity/Unreal

不是"Bevy 更好"，而是**我们的 agent 运行时本来就在 Bevy 里**。用 Unity 意味着把 rig-ecs 的实体世界
和引擎世界做双份同步，把最贵的状态机部分变成跨引擎桥——那就本末倒置了。RealityKit 能做到
"iOS 开发者不用学 Unity"，靠的也是"UI 和内容在同一个声明式/ECS 体系里"；Bevy 对我们是同一个道理。

## 4. visionOS HIG → Bevy 的落地清单

> HIG 的官方页是前端渲染的，数值以 [Designing for visionOS](https://developer.apple.com/design/human-interface-guidelines/designing-for-visionos)
> 为准；下面标"待复核"的是二手整理里的常见数值，落地前用官方页/真机校准。

| HIG 原则 | 具体做法 | 我们的落地 |
|---|---|---|
| **Spatial layout**：窗口有物理感、位置有含义 | 卡片放在"前弧"里，离用户 0.6–1.0 m；不要放在身后/视野边缘 | `card.rs` 的 `Pose` + `space.rs` 的放置规则 |
| **Ergonomics**：可点元素够大 | 常见指引：眼睛目标 ≥ 60pt（**待复核**）。我们换算成**视角**：最小可点 **2.5°**（1.45 m 处 ≈ 6.3 cm；0.8 m 处 ≈ 3.5 cm） | 卡片交互行高度、按钮尺寸；当前行高 18px ≈ 1.28°，**卡片模式要放大到 ≥ 2.5°** |
| **Eyes & hands**：凝视选择、捏合确认；不要依赖 hover 才可发现 | 悬停高亮可以有（gaze highlight），但**功能不能只在悬停时出现**；提供可见 affordance | `input.rs`：gaze 高亮 + pinch 触发；每个卡片有可见按钮/手柄 |
| **Windows**：窗口承载"以 UI 为主"的内容，保持窗口感（标题栏、边框、尺寸） | 卡片 = 窗口：标题、边框、可拖动、可缩放（ornament 手柄） | `card.rs` 的 chrome + `ornament.rs` |
| **Ornaments**：控件挂在窗口边缘、浮在窗口外（常见：底边重叠 ~20pt，**待复核**） | 每张卡片的操作（关闭/展开/状态）做成 ornament，不塞进内容区 | `ornament.rs`：卡片底部/侧边挂件 |
| **Materials & depth**：用系统 glass 表达层级；不要硬阴影 | 半透明背板 + 细边 + 轻微深度（`WorldLayer`），不用投影 | `bevy_luma` 的 SDF 半透明 + 边框高光 |
| **Comfort**：避免在余光里做大幅运动；避免 0.2 Hz 附近的振荡（**待复核**） | 卡片入场用短、缓的动画；相机不做急加速；缩小/展开在同一位置 | 动画系统（待做）+ `camera_rig` 限速 |
| **Immersive space**：按需沉浸，不是一上来全屏 | 默认"窗口空间"；工具卡可展开成沉浸式阅读视图 | `space.rs` 的 immersion 分级 |
| **Accessibility**：键盘/VoiceOver/动态字号/高对比 | 保留键盘路径；字号可缩放；颜色不只靠色相 | `KeyboardFallback` + 主题 token |

**我们的设计 token（按视角定，不按像素定）**：

| token | 值 | 换算（1.45 m 处） |
|---|---|---|
| 正文最小字号 | 0.8° | ≈ 2.0 cm（我们现在的 13px ≈ 0.92°，够） |
| 最小可点目标 | 2.5° | ≈ 6.3 cm |
| 卡片舒适宽度 | 25–35° | ≈ 0.65–0.9 m |
| 卡片距离 | 0.6–1.0 m | — |
| 层间距（深度） | 1–3 cm | 我们的 `layer_depth = 2 cm` 正好 |
| 动画时长 | 0.2–0.35 s，缓动 | — |

## 5. 架构：在现有四层上加"空间层"

```text
rig-ecs           内核（agent/turn/call/gate/ask）         不变
rig-harness       服务（session/commands/settings/Ask/Pick）不变
rig-feathers      空间视图层：
                    content/  转写、composer、chooser 的内容（复用现有 transcript/pane/look）
                    card/     卡片 = 内容 + 姿态 + chrome + ornament
                    space/    卡片放在哪（前弧、墙、桌）、沉浸分级
                    input/    凝视/捏合/拖拽/缩放 + 键盘兜底
feathers_in_3d    渲染（Mirror + 文字 + 排序 + 裁剪 + 拾取）  不变
```

模块计划（都放 `rig-feathers`，不新开 crate）：

| 模块 | 职责 | 复用 |
|---|---|---|
| `card.rs` | `Card { kind, pose, size, chrome }`；拖动/缩放/吸附；内容仍是"行"（`PanelRows`） | `panels`/`transcript` |
| `space.rs` | 卡片放置规则（前弧、距离带、避让）、沉浸分级、焦点与 dim | `FrameGeometry` |
| `input.rs` | 拾取 → 卡片；gaze 高亮；pinch/select；drag；双指缩放；键盘兜底路由 | `feathers_in_3d::pick` |
| `ornament.rs` | 卡片边缘控件（关闭、展开、状态条目） | `status::line` |
| `composer.rs` | 输入卡片：文本 + 附件 + 语音 + 发送；补全 chips | `editor` |
| `chooser.rs` | picker → 选择卡（列表卡 + 预览卡） | `picker` |

**`frame.rs` 的新定位**：不再是"整个界面"，而是**卡片内部排版 + flat 模式**。
保留它的原因：折行、截断、keep/min_width、`CELL` 度量都是"内容排版"的正确答案，且已有 12 个单测。
`Placement` 在空间模式下只用于卡片内部（或者 flat 演示模式，`RF_FLAT=1`）。

## 6. 路线图

| 阶段 | 目标 | 验收 |
|---|---|---|
| **P0**（已做） | 视图插件同形、帧布局、窗格、picker（列表/预览/多选/树） | 截图 + 21 个单测 |
| **P1 卡片化** | 内容 → `Card`：转写卡、composer 卡、chooser 卡；拖动/缩放/吸附；键盘降级为辅助 | 一个房间里 3 张卡能拖、能叠、能缩放；无键盘也能完成"提问 → 看工具卡 → 确认" |
| **P2 空间布局** | 前弧/距离带放置、ornament、焦点 dim、卡片动画 | HIG 检查表 §8 全绿；卡片距离/角尺寸在 token 范围内 |
| **P3 凝视与手势** | gaze 高亮 + pinch 选择 + 拖拽 + 双指缩放；手机陀螺仪 3DoF 相机 | 无鼠标完成一次完整对话（模拟器里用鼠标当凝视） |
| **P4 沉浸与多 agent** | 沉浸式阅读卡、多 agent 卡片并置、语音输入、空间音频 | 两个 agent 并排工作，各自卡片不互相遮挡 |

**P1 是分水岭**：P1 之后，"终端帧布局"变成"卡片内部排版"，界面的主语从"屏幕"换成"卡片"。

## 7. 风险与硬约束（必须承认）

| 约束 | 影响 | 对策 |
|---|---|---|
| **Bevy 不能产出 visionOS 应用** | 不能上 Apple Vision Pro | 明确"设计迁移"定位；目标平台 = 桌面 3D 窗口 → OpenXR（Quest / Android XR） |
| 本机无头显、无 OpenXR 运行时 | 凝视/手势无法真机验证 | 设备抽象 + 鼠标模拟凝视/捏合；真机阶段补测 |
| 无 `/dev/dri`，LLVMpipe 软渲染 | 3D 卡片多了会掉帧 | 卡片数上限、绘制调用预算、按距离降级（LOD） |
| 位图字放大 ~6× 发糊 | 空间里近看图糊 | 换 MSDF/SDF 字，或按距离切图集 |
| `bevy_ui` 是 2D 布局 | 我们用 Mirror 绕开 | 保持 seam 小（`WorldPanel`），别让业务碰 bevy_ui |
| HIG 数值是二手整理 | 可能不准 | 用官方页/真机校准；标"待复核" |

## 8. 验收检查表（每个 UI 改动都过一遍）

- [ ] 交互元素在卡片里，而不是"整屏切块"
- [ ] 可点目标视角 ≥ 2.5°（换算表见 §4）
- [ ] 卡片在 0.6–1.0 m 距离带、正面 ±60° 前弧内
- [ ] 功能不依赖"悬停才出现"；有可见 affordance
- [ ] 层级用深度/材质表达，不用硬阴影
- [ ] 卡片可拖动/可缩放；缩放不破坏内部排版（折行重算）
- [ ] 键盘能完成同一件事（无障碍/桌面模式）
- [ ] 状态行/ornament 不遮挡内容
- [ ] 动画 0.2–0.35 s，无 0.2 Hz 振荡
- [ ] 帧内绘制调用与文本网格在预算内（软渲染下 ≥ 30 fps）

违反任一条时，在 PR/提交说明里写"例外 + 理由"，否则退回。

## 9. 决策记录

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| D1 | **丢交互，不丢模型**：键位降级为辅助输入 | 领域模型是行为规格；交互是外观 | 键位代码不删，但不再是主路径 |

# 第二阶段设计（2026-11-25 讨论结论）

> 三条前提（用户拍板）：**① 自由摆放 + 轻吸附，吸附是 Niri 式滚动平铺的圆柱版；② 不做 OpenXR 头显，
> 只做桌面端/移动端；③ 不追视觉特效（凝视、玻璃材质），只学 visionOS 的《空间界面设计原则》，

## 11. 圆筒滚动平铺（Niri 式）

### 11.1 为什么是 Niri

Niri（[YaLTeR/niri](https://github.com/YaLTeR/niri)，Rust，GPL-3.0）的窗口管理模型是**滚动平铺**：

- 屏幕是一条**无限横向的列带**：每列有宽度（默认预设 `1/3`、`1/2`、`2/3`，可循环切换），
  列里可以竖着放多扇窗；
- 有个 `view_offset`（连续量，带 `Static / Animation / Gesture` 三种状态）横向滚动；
- 聚焦列是否居中由 `center-focused-column: never | always | on-overflow` 决定，默认 `never`（够看就不动）；
- 另有一层**浮动窗口**（`floating.rs`），自由摆放，和 tiling 互切；
- 滚轮：默认 bind 是 **`Mod+WheelScrollDown` → 切工作区**，带 `repeat` 和 **150ms cooldown**
  （`niri-config/src/lib.rs` 默认 bind 表）；横向滚轮按 tick 累积（`horizontal_wheel_tracker.accumulate(v120/120)`，
  `src/input/mod.rs::on_pointer_axis`）；没有绑定的竖直滚轮交给窗口内容。

把这套东西卷成圆柱，就是"土楼"：

| Niri（2D 无限列带） | 我们（3D 圆柱） |
|---|---|
| 列宽 `1/3, 1/2, 2/3` | 列的**弧宽** `30°, 45°, 60°`（预设、可循环） |
| 列 x 坐标 = 前面列宽累加 | 列角度 = 前面弧宽累加（`θ_i = Σ width_j`） |
| `view_offset` 横向偏移 | 圆柱旋转角 `carousel_angle`（用户固定在圆心） |
| `center-focused-column: always` | **固定取 always**：聚焦列永远在正前方（土楼正门） |
| 列内竖排窗口 | 列内**竖叠卡片**（同一角度、不同高度，Niri 的 tile 切分） |
| 浮动窗口层 | 自由摆放模式（卡片脱离圆柱，拖动） |
| Mod+横向滚轮 / 触摸板横滑 | 横向滚轮 / Shift+滚轮 / 触摸横滑 = 转圆柱 |
| 竖直滚轮给窗口 | 竖直滚轮 = 聚焦卡内部滚动 |

**依赖关系说明**：niri 是 GPL-3.0。我们**只读它的算法与语义**（滚动平铺状态机、居中策略、列宽预设、
滚轮分派），代码自己写，不复制；源码放在 `research/niri/niri-main`（已 gitignore，不进仓库、不参与发布）。

**参考文件索引**（下次读源码直接跳这里）：

| 读什么 | 文件 |
|---|---|
| 列宽预设、`center-focused-column` 默认值 | `niri-config/src/layout.rs` |
| `view_offset` 状态机、居中/够看不动 的公式 | `src/layout/scrolling.rs`（`compute_new_view_offset_centered` / `_fit`、`ViewOffset`） |
| 滚轮分派、tick 累积、cooldown | `src/input/mod.rs::on_pointer_axis`、`niri-config/src/lib.rs` 默认 bind 表 |
| 浮动窗口层 | `src/layout/floating.rs` |
| 列内 tile 竖分 | `src/layout/tile.rs` |
| 视口尺寸/缩放 | `src/layout/monitor.rs` |

### 11.2 几何（可直接实现的公式）

用户固定在原点，看向 -Z。第 `i` 列：

```text
θ_i      = Σ_{j<i} width_j                     # 累积弧（度）
θ_i     += (width_i / 2)                        # 到该列中心
angle    = carousel_angle - θ_i                 # carousel_angle 使聚焦列中心对齐 0°
pos_i    = R * (sin(angle), 0, -cos(angle))     # 卡片中心在半径 R 的圆上
rot_i    = 朝向圆心（卡片法线指向用户）
w_px     = 2 * R * tan(width_i / 2) / UNITS     # 切向卡片的像素宽（与弧宽一致）
```

初值：`R = 1.0 m`、`width = 30°`、列高 `H = 0.8 m`（≈24 行）、卡宽 `2·1.0·tan15° = 0.536 m`（≈38 列）。
水平视场 67° 时，正前方 1 张全脸、±30° 与 ±60° 各 1 张斜着"露边"——土楼的样子。

### 11.3 交互（桌面 + 移动，不用凝视/手势）

| 动作 | 桌面 | 移动 | Niri 对应 |
|---|---|---|---|
| 转到上一/下一列 | 横向滚轮 / Shift+滚轮（一格一列，**150ms cooldown**，按住 repeat） | 左右滑（连续，松手吸附到最近列） | `focus-column-left/right` + 动画 |
| 卡内容滚动 | 竖直滚轮（在卡片上） | 上下滑 | 竖直滚轮给窗口 |
| 聚焦 | 点击卡片 | 点按 | 点击窗口 |
| 切列宽预设 | `[` `]` 或 ornament 按钮 | 双指缩放？先不做 | `switch-preset-column-width` |
| 拖成自由摆放 | 拖卡片离开圆柱 | 长按拖动 | `move-window-to-floating` |
| 吸附回圆柱 | 拖到半径/角度容差内松手 | 同左 | `move-window-to-tiling` |
| 键盘兜底 | ←/→ 换列、↑/↓ 卡内滚动、Tab 切卡、Enter 确认 | — | 键位绑定 |

**吸附判定**：松手时若 `|pos| ∈ R ± 10%` 且与该列角差 `< width/2`，吸附到最近列（必要时插入列）；
否则留在自由摆放层。这就是"轻吸附"——不强制，但靠近就贴。

### 11.4 卡片 = Niri 的 tile

- 一个**列**有 `arc`、`height`（= 视高带）、`tiles: Vec<CardId>`；
- 列内 `tiles` 竖分高度（Niri 的 tile 切分），gap 固定 8 px；
- 卡片有 `title`、`kind`、`state`，内容仍是"行"（`PanelRows` 那套：折行、截断、keep）；
- 卡片 chrome 极简：圆角 + 细边 + 标题行；**不做玻璃/发光**（前提③），只用 `WorldLayer` 的深度和明暗。

# 第三阶段设计：斗兽场模型（2026-11-25 二次讨论）

> 用户修正：不做"土楼圆柱"，做**罗马斗兽场漏斗**——太阳（摄像机）在中心，卡片是引力漏斗上运行的行星；
> 层内多卡按**行**排列；自由摆放被约束在**所属层级的轨道球体**上；弹窗是卡片的**卫星**。
> 本节取代 §11 的几何；§11 的 Niri 语义（滚动/吸附/居中/预设宽）仍然有效，只是换了个形状。

## 13.1 词表（先对齐，避免后面用错词）

| 用户的话 | 几何对象 | Niri 对应 |
|---|---|---|
| 斗兽场 / 漏斗 | 以 Y 轴为中心、开口向上的圆锥台 | workspace |
| 第 N 行座位 | 第 `L` **层**：水平圆环，半径 `R_L`、高度 `Y_L` | column |
| 一列内多卡 | 同一层里沿环排开的**多张卡**（层内多卡是 P1 就要有的） | column 里的多个窗 |
| 座位 | 层上的**槽位**（角度 `θ = k·Δθ`） | 列的位置 |
| 太阳 | **摄像机**（在轴上，高度 `Y_F` = 聚焦层） | view offset |
| 行星 | **卡片** | window/tile |
| 卫星 | 卡片的**浮层/弹窗**（picker、补全、确认），绕卡片转、永远朝相机 | overlay |
| 轨道球体 | 以该层中心为球心、半径 `R_L` 的球面（卡片只能在这上面移动） | floating 层 |

## 13.2 几何（初值，可调）

```text
层 L：   R_L = R0 + L·ΔR        （R0 = 1.00 m, ΔR = 0.25 m）
        Y_L = Y0 + L·ΔY        （Y0 = 0.00 m, ΔY = 0.35 m）
        Δθ  = 26°              （一圈最多 14 个座位）
槽位 k： θ   = k·Δθ
卡中心： P   = (R_L·sin θ,  Y_L ,  -R_L·cos θ)      # 摄像机看向 -Z
卡宽：   w   = 2·R_L·sin(Δθ/2) − gap                # 切向弦长，外层更宽
                L=0: 0.42 m ≈ 30 列   L=1: 0.52 m ≈ 37 列   L=2: 0.62 m ≈ 44 列
朝向：   每帧 look_at(摄像机)                        # billboard（饥荒式）
```

**"阳光照到所有行星"的准确含义**（这条是真的）：同一层上的卡片到中心等距、都朝内（billboard 后都正对相机），
所以**同层卡片之间永远不会互相遮挡**——这正是一块平面屏幕做不到的。一圈 360°、视野 67°，所以一次看到约 1/5 圈，
横向滚动（转环）把别的座位带到正前方。外层半径更大，因此**外层卡可以更宽**（30 → 37 → 44 列）。

**一条需要纠正的说法**："卡片长度可以无限制加长不会造成上下两行重叠"——只在**同层**成立。
卡片是竖直平板，长高会伸进上一层的视线（上一层的卡在更高、更外的地方）。两种处理：

- (a) **聚焦即屏蔽**：相机升到第 L 层时隐藏所有 `< L` 的层（用户原方案），长卡只管挡住**上层**；上层本来就只是"背景"。
- (b) **卡高上限 = 层距 − gap**：任何时候都能看到上一层，但长文档卡会被压扁。

初版取 (a)：缺省卡高 0.45 m（≈14 行），长文档卡 0.70 m（≈21 行），都允许超过层距 `ΔY = 0.35`。

**层高 / 相机**：`Y_cam = Y_F`（与聚焦层平齐），升降层时相机沿轴移动 `ΔY`；视角 pitch = 0（平视），
所以聚焦层的卡中心正好在视线高度上。

## 13.3 轨道约束（自由摆放）

- 卡片的主坐标存**漏斗坐标**：`(layer, azimuth, elevation)`。
- 自由拖动时，卡片被锁在**该层的轨道球面**上：
  `P = (0, Y_L, 0) + R_L · dir(azimuth, elevation)`（2 个自由度：绕环、升降）。
- 松手吸附：`elevation` 拉回 0（回到座位面），`azimuth` 吸附到最近槽位；若离座位太远，就插一个新槽位。
- 卫星（弹窗）：`P_sat = P_card + r_sat · dir(azimuth_sat, elevation_sat)`，`r_sat ≈ 0.15 m`，
  同样 billboard，画在 `WorldLayer(2)` 上（卡片 0，主层 0，浮层 2）。

**billboard 的可行性已经验过**：`feathers_in_3d/src/pick.rs` 的拾取是**带变换**的
（用 `anchor.rotation` 做法线、`anchor.to_matrix().inverse()` 把命中点换到面板局部），
所以卡片绕相机转不影响点击；文字网格是面板根的子实体，跟着转。

> 关于"爱因斯坦水星进动"：水星近日点进动是广义相对论的修正量，不是"轨道分布"的公式，
> 拿它算层半径没有意义。这里真正要的"引力模型"是两条：**每层一个固定轨道半径**（层半径由漏斗几何给出）
> 和 **卡片只能在球面上移动**。要更好看的层距，用等比 `R_L = R0·q^L`（q ≈ 1.2）；要"行星"感，
> 可以给每张卡一个缓慢的角速度做公转动画（可关）。

## 13.4 交互（桌面 + 移动，Linux/Android 优先）

| 动作 | 桌面 | 移动 | 说明 |
|---|---|---|---|
| 环内转环（Niri 滚动） | 横向滚轮 / Shift+滚轮 | 左右滑 | 一格一座位，**150 ms cooldown**，松手吸附到最近座位（niri 的 tick 累积 + cooldown） |
| 升降层 | 竖直滚轮（在空白处） | 上下滑（空白处） | 相机移 `ΔY`；升起时隐藏下面的层 |
| 卡内滚动 | 竖直滚轮（在卡片上） | 卡内上下滑 | 与 niri 一致：竖直滚动先给"指针下的东西" |
| 聚焦 | 点击卡片 | 点按 | 聚焦卡居中（转环到它） |
| 拖卡 | 拖动 | 长按拖动 | 锁在轨道球面；松手吸附 |
| 弹窗 | 点卡片上的按钮/确认 | 点按 | 卫星卡，永远朝相机 |
| 键盘兜底 | ←/→ 转环、↑/↓ 升降层、Tab 切卡、Enter 确认、PgUp/PgDn 卡内滚动 | — | 无障碍 + 桌面 |

## 13.5 Niri 语义怎么保留

- **滚动 = 转环**（横向），**换层 = 升降**（竖直）：niri 的 `view_offset` 变成 `carousel_angle`（绕 Y 轴）+ `camera_layer`（沿 Y 轴）。
- **居中**：取 niri 的 `center-focused-column: always` → 聚焦座位永远在正前方（`angle = -k·Δθ` 的补角）。
- **列宽预设**：niri 的 `1/3, 1/2, 2/3` → 我们的**弧宽预设** `26° / 39° / 52°`（`[` `]` 切换），
  弧宽变了，座位数在同一层里就变（26° 时 14 座，52° 时 7 座）。
- **浮动层**：niri 的 floating → 轨道球面上的自由摆放（§13.3）。
- **tick 累积 + cooldown**：`src/input/mod.rs::on_pointer_axis` 的 `horizontal_wheel_tracker.accumulate(120)` 与默认 bind 的
  `cooldown-ms=150`，直接照抄这两个数值。

## 13.6 与 §11 的差异

| §11（土楼圆柱） | §13（斗兽场漏斗） |
|---|---|
| 卡片在等半径圆柱面上，按累积弧排列 | 卡片在**分层**圆锥台上，外层半径更大、卡更宽 |
| 换列 = 绕轴转 | **换层 = 相机升降**；绕轴转 = 层内换卡 |
| 视图固定在同一高度 | 相机高度 = 聚焦层的 `Y_L`，下层隐藏 |

# 第四阶段设计：两级视角（2026-11-25 三次讨论）

## 14.1 层级：恒星 → 行星 → 卫星

```text
恒星（用户 = 摄像机）在中心
  └─ 轨道层 L = 一颗行星 = 一个 agent / 会话
       └─ 卫星 = 该 agent 的卡片（转写、工具、确认…），沿轨道排开
```

- **总览视角（进入应用时）**：所有行星的轨道都在恒星面前，各自排满卫星；相机在第 `L` 层的 `Y_L` 上，
  `L` 以下的层**隐藏**，`L` 以上是固定高度的"背景卡"。
- **进入行星视角**：只留这一个 agent，其余行星隐藏；该 agent 的卡改成 **Niri 式滚动平铺的一行**
  （横向滚动、聚焦卡居中、可读尺寸）。**多卡的出路是"进行星"，不是加座位**。

## 14.2 总览里的高度规则（回答问题 2）

| 位置 | 行为 |
|---|---|
| 当前聚焦层 **选中卡** | 可以**向下无限展开**（下方更近的层已隐藏，不会撞到别人） |
| 当前聚焦层其它卡 | 固定高度（缺省 0.45 m） |
| **更近恒星的下层**（`< L`） | **隐藏不显示** |
| **更远的层**（`> L`） | 卡片**不展开、固定高度**，当背景 |

所以"长卡片不受限制"在总览里成立的方向是**向下**（用户说的方向），向上/向外仍受层距约束——这也是为什么
更远的层要"固定高度不展开"。

## 14.3 数据结构

```rust
struct Planet { agent: Entity, layer: u16 }            // 轨道层 = 行星
struct Card { layer: u16, slot: u16, kind: CardKind, height_m: f32, expanded: bool }
struct Funnel { radius0, radius_step, height0, height_step, arc, gap }
enum Mode { Overview, Planet(Entity) }                  // 两级视角
```

- `Mode::Overview`：相机 `Y = Y_layer`，按 §13.2 摆环 + billboard；
- `Mode::Planet(agent)`：相机移到该层前方，卡片改排成一行（`x = k·(w+gap)`，`y = Y_layer`，`z = -R`），
  仍是 billboard；横向滚动 = Niri 的 `view_offset`；
- 切换：相机沿轴/径向 interpolate + 其余层隐藏（无花哨动效，前提③）。

## 14.4 待确认（旧）

1. 层 = 一个 agent/会话 → **确认：是**。
2. 长卡挡上层 → **确认：更远的上层固定高度、不展开**。
3. 一层超过 14 座 → **确认：进行星视角用 Niri 滚动平铺管理，不在总览里加座位**。

# 17. 圆柱环平铺：一个几何硬约束（2026-11-25）

用户定案：**把漏斗改成圆柱体——每层一圈环形平铺，层沿上下堆叠；每层半径按该层窗口多少调整。**
问题 2/3 的"远层只留标题条、底部层指示条"已同意（下一步做）。

## 17.1 环形 = 一圈要装下 N 列，每列占 `360°/N`

| 每层列数 N | 每列角度 | 从中心看的效果 |
|---|---|---|
| 3 | 120° | 一张卡填满视野，文字 ≈2.7°/格（像把手机贴脸上），不可读 |
| 6 | 60° | 一张半卡，文字 ≈1.3°/格 |
| 12 | 30° | 约 2.5 张卡，文字 0.8°/格（**可读**，正好是现在 1 m 处的字号） |
| 20 | 18° | 约 4 张卡，文字 0.5°/格（偏小） |

也就是说：**"一圈装满 N 列 + 在圆心的相机"要可读，N 得 ≥ 12。** 但一个 agent 通常只有 2–4 张卡
（转写/工具/确认/composer），这时每列 90–120°，从中心看是一张糊脸的大卡。

半径按窗口数调整（`R = N·w / 2π`）正是"装得下"的做法，但它同时决定了"看得清"：
N=3、w=0.42 m 时 `R ≈ 0.20 m`，卡片离眼睛 20 cm。

## 17.2 两条能同时成立的路线

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. 环只占前弧** | 相机在中心；卡片只铺前方 120° 弧，半径固定 1.0 m（0.8°/格）；一弧 ≈ 4 列（30°），超过就开新层 | 不是"整圈"，但读得清、斗兽场感还在 |
| **B. 整圈 + 相机在环外** | 每层整圈铺满，`R = N·w/2π`（窗口多 → 环大）；相机退到环外 `R + 1.0 m`，像旋转木马；层沿 Y 堆叠 | 放弃"恒星在中心"；层多时要拉很远 |
| **C. 两级各用一种** | 总览 = B（看圆柱，远层只留标题条）；进入 agent = 现在的平面 Niri（可读性最好） | 两套机位/两套几何，但各自最优 |

我推荐 **C**：它刚好对应"总览 / 进入 agent"两级，也保住了已经写好的 `niri.rs`（平面 Niri 原样用于
agent 视角），总览再加一层"环形摆放"（`R = N·w/2π` + 环外相机 + 每层一圈）。

# 18. 定案 C + "首尾相连的带鱼屏"：实现时撞到的硬约束（2026-11-25）

用户定案：**C（两级各用一种）**，并且：
- 单 agent 视角的平面 Niri 在左右切换时也**首尾相连**（圆柱），像一条特别宽的带鱼屏；
- **弹窗也走平铺**，不做浮层；
- 不切左右时**只显示当前聚焦的那一屏**；
- 总览 = 几个这样的环形带鱼屏**上下堆叠**。

## 18.1 已经实现的（`niri.rs`，35 个单测）

- `Tiling::ring: Option<f32>`：环模式。`ring_angle(meters) = meters / R`；
- `target_offset` 在环模式下**不夹取**，并且 `wrap_offset` 取"离当前最近的一圈"——
  从最后一列回到第一列是向前滚一小步，不是倒滚一圈；
- `place_tiles` 环分支：卡片放在 `(R·sinθ, Y, −R·cosθ)`，朝圆心（相机在圆心）；
- **只显示聚焦屏**：滚动停下（`|offset-target| < 4 mm`）后只留聚焦列，其它列藏起来；
- 平面模式（`ring = None`）原样保留 = 总览/对比用。

## 18.2 撞到的硬约束：镜头

把内容铺满一圈时，一列占的**角度**是 `360° × 列宽 / 总宽`——**和半径无关**。
所以"首尾相连"要真正无缝，必须 `总宽 = 2πR`（内容正好绕一圈）。于是：

| 每层列数 | 每列角度 | 从圆心看 |
|---|---|---|
| 3 | 120° | 一张卡占 1/3 圈，文字 ≈4°/格（贴脸） |
| 6 | 60° | ≈2°/格 |
| 12 | 30° | ≈0.8°/格（正好可读） |

也就是说：**"首尾相连 + 几个列"在几何上必然让每列变得极宽**。一个 agent 只有 2–4 张卡时，
要么接受"每一屏都很大、看不了全貌"，要么让这条带鱼屏**真的有很多列**（把转写切成多列 /
加入空白槽位把一圈补满），要么单 agent 视角仍用平面、只有总览用环。

## 18.3 需要拍板

A. **带鱼屏有很多列**：转写按列切（每列 ~30 列字），一圈 12 列 = 360°，可读且真正无缝；
B. **一圈只有几列、但接受每列 90–120°**（相当于"手边三块大屏"），半径按 `总宽/2π` 缩到 0.2–0.3 m；
C. **单 agent 视角回到平面 Niri**（今天的实现），环只用在总览的上下堆叠里。

我倾向 A：它同时满足"首尾相连""带鱼屏""可读"，代价是转写要从"一行行长文本"改成"分列"。

# 20. 定案 A：短带鱼屏不绕圈（2026-11-25）

## 20.1 为什么之前看着不像"贴在内壁上"

环模式里所有层共用同一个半径是对的，但**层间高度还在用漏斗的 0.30 m**，而一条带鱼屏有 0.72 m 高——
两层直接叠在一起，看起来是一团卡片而不是内壁上的两条带。修正：

```text
环模式  layer_y = L × (viewport.y × scale + 0.06)
```

现在（`render/rf_ring/01_overview.png`）相机在轴心、第 0 层在眼前：转写居中，
`search_products` / `create_order` 往右弯过去、边缘收拢，是一条**贴着内壁的 Niri 带**；
短带鱼屏只占 85° 弧，所以不首尾相连、滚到两端为止。上面那层被 45° 竖直视野挡在画外，
要靠总览里的自由相机抬头/移动才看得到——这正是"手动凑近看"的用法。
